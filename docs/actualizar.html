Actualizar el sistema

Bajar cambios de GitHub y aplicarlos en el servidor. Cada paso indica qué hace y por qué es necesario.

Siempre respalde antes de actualizar

Las actualizaciones pueden incluir cambios en la base de datos (migraciones). Si algo falla a mitad del proceso, el respaldo es su única forma de volver al estado anterior sin perder datos.

Respaldos en nube y cron → Respaldos.

Usa los scripts del repositorio. Recomendado en producción: menos errores y orden garantizado.

Copiar y pegar (recomendado) 
cd ~/sgaf
git pull origin reingenieria
./scripts/deploy.sh --backup
  1. Paso 1 — Conectarse por SSH al servidor

    Abrir una terminal remota en el Ubuntu donde ya corre SGAF.

    Por qué SGAF no se actualiza desde su PC Windows: el código y Docker están en el servidor. SSH es la forma segura de ejecutar comandos allí.

  2. Paso 2 — Ir a la carpeta del proyecto 
    cd ~/sgaf

    Todos los comandos de deploy deben ejecutarse desde la raíz del repositorio.

    Por qué docker compose y los scripts buscan docker-compose.yml y .env en esa carpeta. Si está en otro directorio, los comandos fallan o usan configuración incorrecta.

  3. Paso 3 — Bajar los cambios desde GitHub 
    git pull origin reingenieria

    Trae al servidor el código que subió el desarrollador desde su PC.

    Por qué El servidor solo tiene una copia local del código. git pull sincroniza esa copia con la rama reingenieria en GitHub. Sin este paso, seguiría corriendo la versión antigua.

  4. Paso 4 — Desplegar con respaldo automático 
    ./scripts/deploy.sh --backup

    Un solo comando: respalda la BD, reconstruye contenedores, aplica migraciones y archivos estáticos.

    Por qué El flag --backup guarda un .sql en ~/sgaf_backups/ antes de tocar nada. Luego el script actualiza Docker (nuevas imágenes si cambió código), ejecuta migrate (tablas nuevas o modificadas) y collectstatic (CSS/JS del admin Django). Es el equivalente seguro a hacer todo manualmente.

  5. Paso 5 — Verificar que los servicios están activos 
    docker compose ps

    Confirma que los cuatro contenedores muestran estado Up.

    Por qué Si un contenedor está detenido o reiniciando en bucle, la web no responderá o fallará la firma. Revisar aquí evita asumir que “terminó bien” cuando en realidad el backend no arrancó.

    Deben estar Up: sgaf_db_prod, sgaf_backend_prod, sgaf_frontend_prod, sgaf_firma_dep.

  6. Paso 6 — Probar en el navegador

    Abrir la URL del sistema (la de SGAF_PUBLIC_URL en .env) e iniciar sesión.

    Por qué docker compose ps solo confirma que los procesos corren, no que la aplicación responde bien. Un error de CORS, migración incompleta o frontend viejo solo se nota al usar la web.

Casos especiales

SituaciónQué hacerPor qué
Cambió menús, modales o bandejaDeploy completo o docker compose up -d --build frontendEl frontend es una imagen Docker; sin rebuild sigue mostrando la UI antigua aunque el código en disco ya cambió.
Solo cambió API backenddocker compose restart backendPython se recarga al reiniciar; no hace falta rebuild si no cambió dependencias ni Dockerfile.
Login error 400./scripts/sync_env_network.sh + docker compose up -d backendDjango rechaza peticiones si la URL del navegador no está en ALLOWED_HOSTS o CORS.

Opciones de deploy.sh

ComandoQué haceCuándo usarlo
./scripts/deploy.sh --backupRespaldo + actualización completaProducción habitual. Siempre que actualice con datos reales.
./scripts/deploy.shActualiza sin respaldoSolo en entornos de prueba donde puede perder datos.
./scripts/deploy.sh --quickSolo reinicia contenedoresCuando no hubo cambios de código ni migraciones; no actualiza pantallas.

Mismos pasos que deploy.sh, uno por uno. Útil para entender el proceso o si el script falla.

Orden obligatorio Respaldo → git pull → Docker → migraciones → estáticos. No invertir el orden: migrar sin respaldo o sin contenedores actualizados causa errores graves.
Bloque completo (copiar y pegar) 
cd ~/sgaf
mkdir -p ~/sgaf_backups
STAMP=$(date +%Y%m%d_%H%M%S)
docker exec sgaf_db_prod pg_dump -U sgaf_user sgaf_db \
  > ~/sgaf_backups/respaldo_${STAMP}.sql
ls -lh ~/sgaf_backups/respaldo_${STAMP}.sql
git pull origin reingenieria
docker compose up -d --build
docker exec sgaf_backend_prod python manage.py migrate --noinput
docker exec sgaf_backend_prod python manage.py collectstatic --noinput
docker compose ps
  1. Paso 1 — Ir al proyecto 
    cd ~/sgaf

    Ubicarse en la raíz del repositorio en el servidor.

    Por qué Docker Compose y los archivos de configuración están en esta carpeta. Otros directorios no tienen el contexto correcto para desplegar.

  2. Paso 2 — Respaldo de base de datos (obligatorio) 
    mkdir -p ~/sgaf_backups
STAMP=$(date +%Y%m%d_%H%M%S)
docker exec sgaf_db_prod pg_dump -U sgaf_user sgaf_db \
  > ~/sgaf_backups/respaldo_${STAMP}.sql
ls -lh ~/sgaf_backups/respaldo_${STAMP}.sql

    Exporta toda la BD a un archivo de texto SQL con fecha en el nombre.

    Por qué Las migraciones pueden alterar tablas y columnas. Si una migración falla a medias, la BD queda inconsistente. El pg_dump es una “foto” recuperable con psql. ls -lh confirma que el archivo existe y no está vacío.

    Use DB_USER y DB_NAME de su .env.

  3. Paso 3 — Bajar cambios de GitHub 
    git pull origin reingenieria

    Actualiza el código fuente en el servidor.

    Por qué Sin git pull, Docker reconstruiría las mismas versiones antiguas. Este paso trae el código nuevo que debe empaquetarse en los contenedores.

  4. Paso 4 — (Opcional) Revisar .env si cambió IP o dominio 
    nano .env

    Solo si el acceso por URL nueva da error 400 al iniciar sesión.

    Por qué Django valida el host y el origen de cada petición. Si movió el servidor o accede por otro nombre, debe listar esa URL en ALLOWED_HOSTS, CORS y CSRF. El script sync_env_network.sh hace esto automáticamente en modo script.

    VariableEjemploPara qué
    ALLOWED_HOSTSlocalhost,192.168.1.50,svtestHosts que Django acepta
    CORS_ALLOWED_ORIGINShttp://192.168.1.50Origen del frontend en el navegador
    CSRF_TRUSTED_ORIGINSIgual que CORSPermite el formulario de login
    SGAF_PUBLIC_URLhttp://192.168.1.50URL pública del sistema
    VITE_API_URLhttp://192.168.1.50/apiURL del API para el frontend
  5. Paso 5 — Reconstruir y levantar contenedores 
    docker compose up -d --build

    Compila imágenes con el código nuevo y reinicia los servicios en segundo plano.

    Por qué Los contenedores encapsulan frontend, backend, base de datos y firma-dep. --build asegura que cambios en código o dependencias entren en la imagen. Sin build, solo reinicia lo que ya estaba empaquetado.

    Solo pantallas: docker compose up -d --build frontend
    Solo reiniciar sin cambios: docker compose up -d

  6. Paso 6 — Aplicar migraciones 
    docker exec sgaf_backend_prod python manage.py migrate --noinput

    Actualiza la estructura de tablas según los modelos del código nuevo.

    Por qué Cuando el desarrollador cambia modelos Django, genera archivos de migración. migrate los ejecuta en PostgreSQL (nuevas tablas, columnas, índices). Si salta este paso, la app puede crashear al usar funciones nuevas.

  7. Paso 7 — Recolectar archivos estáticos 
    docker exec sgaf_backend_prod python manage.py collectstatic --noinput

    Copia CSS, JS e imágenes del admin Django a la carpeta que sirve el servidor.

    Por qué El panel de administración y algunos assets del backend no van en el frontend React. collectstatic los deja listos para que nginx/backend los entregue correctamente.

  8. Paso 8 — Verificar 
    docker compose ps
docker exec sgaf_backend_prod python manage.py check

    Revisa contenedores y configuración Django.

    Por qué ps confirma que todo está Up. manage.py check detecta errores de configuración antes de que un usuario los encuentre en producción.

    Abra SGAF_PUBLIC_URL en el navegador y pruebe el login.
